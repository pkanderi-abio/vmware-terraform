# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

Terraform that provisions a highly-available RKE2 (Rancher Kubernetes Engine 2) cluster on VMware vSphere: 3 control-plane nodes fronted by a `kube-vip` (ARP mode) virtual IP, plus N worker nodes. VMs are cloned from a pre-built cloud-init-enabled template and configured entirely through cloud-init (via the VMware GuestInfo datasource) — no vSphere guest customization specs are used.

## Storage: migrated off LAB-CL01 to K8S-CL01 (vSAN) — 2026-08-24

This cluster used to run on `LAB-CL01` (4 ESXi hosts, single NIC each, storage on a Synology LUN — `LAB-LUN01` — presented over single-path software iSCSI with zero multipathing). That single-path iSCSI setup was root-caused (via direct vCenter `EventManager` queries, not inference) as the source of a long-running, severe incident: dozens of `Lost access to volume ... due to connectivity issues` / `Successfully restored access` event pairs, ext4 journal-abort storms on worker nodes, etcd `fdatasync` calls taking 5–15s against a 1s budget, and `kube-vip`/CSI-controller crash-looping — because vCenter's own management traffic and the LUN's iSCSI traffic shared the same single physical NIC per host, any blip on that one path took down both at once. The vSphere CSI driver itself was fully regression-tested and ruled out as a cause during that investigation.

**Resolution**: the cluster (`terraform.tfvars`) now targets `K8S-CL01` — 2 ESXi hosts, 4 physical NICs each, with vSAN storage and *dedicated, separate* physical NICs/VLANs for vSAN traffic and vMotion, isolated from management traffic entirely. This is a genuine fix for the original root cause (a shared, single-path network fabric), not a workaround. `LAB-CL01`/`LAB-LUN01` are retired; nothing in this repo should reference them going forward. Real, honest I/O testing against `vsanDatastore` post-migration (`dd` with `fsync`/`O_DIRECT`, plus a forced cross-node volume reattach with checksum verification) showed ~82MB/s write / ~100MB/s read with perfect data integrity across the reattach.

**Known tradeoff, not a defect**: `K8S-CL01` has only 2 hosts and no witness appliance, so vSAN objects run at `FTT=0` (no storage-level redundancy — see the storage-policy rough edge below) — this migration fixes the *network* single-point-of-failure that caused the original incident, it does not add storage redundancy. A 3rd host or a witness appliance would be needed for real FTT=1 protection, and the witness route was tried and abandoned this session because the vSAN network (`10.10.10.x`) is physically isolated from the only network the witness could sit on (`192.168.100.x`) with no routable path between them.

**If `observe-dev` (Loki/Mimir/Tempo/MinIO/Grafana) is still needed**: it is not managed by this Terraform and was not part of the K8S-CL01 migration — it lived on `LAB-CL01`'s PVs, which no longer exist post-rebuild. It will need to be redeployed from scratch on `K8S-CL01` if still wanted; don't assume it's already running there.

## Commands

```bash
terraform init
terraform fmt -recursive      # format all .tf files before committing
terraform validate
terraform plan
terraform apply
```

There is no test suite. [.github/workflows/terraform.yml](.github/workflows/terraform.yml) runs `fmt -check`, `validate`, and `tfsec` on every push/PR (no vCenter credentials involved — it can't catch data-source lookup errors). `terraform plan` against real vCenter credentials is the only way to catch those (bad datacenter/cluster/datastore/network/template names).

## State management

State is a **local file** (`terraform.tfstate`), not a remote backend — deliberately, not just by default. A natural remote-backend candidate would be an in-cluster MinIO (`observe-dev` used to run one on `LAB-CL01`, backed by the same storage that's since been retired — see "Storage" above), but `observe-dev` isn't part of this Terraform and doesn't currently exist on `K8S-CL01`. Revisit a MinIO-backed `s3`-compatible backend only after redeploying and confirming it's genuinely healthy on the new cluster; don't build on storage you haven't verified.

In the meantime:
- `terraform.tfstate`, `terraform.tfstate.backup`, `terraform.tfvars`, and `.env` all contain plaintext secrets (`rke2_token`, `vsphere_password`, `registry_password`, ...) — Terraform does not encrypt sensitive values in local state, it only redacts them from CLI output. Keep these at `chmod 600`; they are not just gitignored, they should never be group/world-readable on disk either.
- **Back up `terraform.tfstate` before any risky operation** (a `-replace`, a provider upgrade, restructuring resources) — copy it somewhere outside the repo. There's no automated backup; this is a manual discipline until a real remote backend is available.
- If the state file is ever lost, this cluster is *not* unrecoverable — the actual infrastructure still exists in vSphere/Kubernetes — but Terraform loses track of it, and reconstructing state (via `terraform import`, one resource at a time) is real, tedious work. Treat the state file with the same care as the credentials it contains.

Before `apply`, copy `terraform.tfvars.example` to `terraform.tfvars` and fill in real values. vCenter credentials are **not** set via `terraform.tfvars` — export them instead, since the provider (`providers.tf`) reads them from the environment by default:

```bash
export VSPHERE_USER=administrator@vsphere.local
export VSPHERE_PASSWORD=...
export VSPHERE_SERVER=vcenter.example.com
```

After a successful apply, `terraform output kubeconfig_fetch_command` prints the command to pull a working kubeconfig off the primary control-plane node.

## Architecture

**Bootstrap ordering is the crux of this repo.** RKE2 HA requires the VIP to be live before the second and third control-plane nodes (and any workers) can join, and VM creation completing in vSphere does *not* mean cloud-init/RKE2 has finished inside the guest. [main.tf](main.tf) enforces the real ordering explicitly:

1. `module.control_plane_primary` — the only node created with `cluster-init` semantics (`is_primary = true` in its cloud-init render). It also ships the `kube-vip` DaemonSet manifest into `/var/lib/rancher/rke2/server/manifests/`, which RKE2 auto-applies once its own apiserver is up. Because `kube-vip` becomes a cluster-wide DaemonSet object, it only needs to be placed on this one node — RKE2 schedules it to all control-plane nodes once they join.
2. `null_resource.wait_for_primary` — SSHes into the primary node and blocks on `cloud-init status --wait`, then `rke2-server` being active, then the VIP itself answering `/readyz`. This is the synchronization point between "VM exists" and "cluster is actually joinable."
3. `module.control_plane_secondary` (for_each over indices `"1"`, `"2"`) and `module.workers` (for_each over worker indices) both `depends_on = [null_resource.wait_for_primary]` and join via `server: https://${control_plane_vip}:9345`.

Node identity (hostname, static IP, RKE2 role) is driven by list index, not by any dynamic discovery: `var.control_plane_ip_addresses` and `var.worker_ip_addresses` are positional, matched up with `local.control_plane_names` / `local.worker_names` in [locals.tf](locals.tf). Changing cluster size means resizing these lists (worker count) or is unsupported by design (control-plane count is hardcoded to 3 — see the `validation` block on `control_plane_ip_addresses` in [variables.tf](variables.tf)).

**modules/vm** ([modules/vm/main.tf](modules/vm/main.tf)) is a thin, role-agnostic wrapper around `vsphere_virtual_machine` clone: it takes already-rendered `userdata`/`metadata` strings, base64-encodes them, and injects them via `extra_config["guestinfo.userdata"]` / `["guestinfo.metadata"]`. All three call sites in [main.tf](main.tf) (primary, secondary control-plane, workers) render cloud-init from the same two template families but with different variables — that's the only thing that differs between a control-plane and worker node at the Terraform level.

**Cloud-init templates** (`templates/cloud-init/*.tpl`) are plain `templatefile()` inputs, not Terraform-aware — Terraform interpolation happens once at render time in main.tf, and the `%{ if is_primary ~}` conditional in [control-plane-userdata.yaml.tpl](templates/cloud-init/control-plane-userdata.yaml.tpl) is what differentiates the primary node (gets the kube-vip manifest, omits `server:`) from secondary control-plane nodes (gets `server: https://<vip>:9345`, no kube-vip manifest). The kube-vip DaemonSet manifest itself ([templates/manifests/kube-vip.yaml.tpl](templates/manifests/kube-vip.yaml.tpl)) is rendered separately in [locals.tf](locals.tf) and passed into the control-plane template pre-base64-encoded, embedded via cloud-init's `encoding: b64` file directive — this sidesteps YAML-in-YAML indentation problems rather than trying to inline a multi-doc Kubernetes manifest inside a cloud-config `write_files` block.

**Cluster join secret** is a pre-shared `var.rke2_token` (generate with `openssl rand -hex 32`), not RKE2's auto-generated token — this avoids needing a remote-exec round trip to read the token off the primary node before other nodes can be configured, at the cost of the operator having to pick and distribute the token themselves.

## Prerequisites

Before the first `terraform apply` against a new vCenter, gather:

- **The template itself**: `var.template_name` must reference an existing vSphere VM template with cloud-init installed and the **VMware GuestInfo datasource** enabled (default on stock Ubuntu 22.04+ cloud images). This repo does not build that template — it assumes one already exists. If asked to build one, that's a separate concern (e.g. Packer), not something wired into this Terraform. The template's own virtual hardware version doesn't need to be fixed up by hand first — `modules/vm` explicitly sets `hardware_version = 20` on every clone regardless of what the template shipped with (see "Storage" below). It also *attempts* to blank the `vapp.properties` map (a real leaked password and an unrelated SSH key baked into this template's OVF), but that blank-out is confirmed not to actually persist and `vapp` is now in `lifecycle.ignore_changes` — see the "vApp" rough edge under "Known rough edges" below before assuming this is a working mitigation.
- **The real network subnet** for `var.vsphere_network` — see the "Don't trust a portgroup name" rough edge below. Don't fill in `control_plane_ip_addresses`/`worker_ip_addresses`/`control_plane_vip`/`network_gateway` from guesswork or the `terraform.tfvars.example` placeholders.
- **The datastore's `ds:///vmfs/volumes/<uuid>/` URL** for `var.vsphere_datastore_url` (used by the CSI StorageClass) — not exposed by the `vsphere_datastore` data source; look it up via the datastore's `summary.url` property (pyvmomi/govc against the same vCenter).
- **vCenter credentials in two places**: `VSPHERE_USER`/`VSPHERE_PASSWORD`/`VSPHERE_SERVER` as env vars for the provider itself, *and* `vsphere_user`/`vsphere_password`/`vsphere_server` in `terraform.tfvars` (same values) for the in-cluster vSphere CSI secret, which Terraform variables can't populate from the provider's own env-var fallback.
- **ESXi host hardware-version support** — confirm your hosts actually support the `hardware_version` value in `modules/vm/main.tf` (query `host.config.product` via pyvmomi/govc); vCenter's own version doesn't guarantee every host it manages supports the same range.
- **If the datastore is vSAN**: confirm what `var.vsphere_storage_policy_name` resolves to is actually satisfiable by the real cluster topology (host count, fault domains, whether a witness exists) *and* actually carries the space-reservation/thin-provisioning behavior you want — don't assume the datastore's own "default" policy designation is either correct or persistent. See the K8S-CL01 rough edges under "Known rough edges" below; this cost a full troubleshooting session on a 2-host vSAN cluster with no witness.

## Storage

RKE2 ships no default StorageClass or CSI provisioner. `null_resource.install_vsphere_csi` in [main.tf](main.tf) installs the [vSphere CSI driver](https://github.com/kubernetes-sigs/vsphere-csi-driver) after the full cluster is up: it SSHes to the primary control-plane node, applies the upstream namespace/RBAC/controller/node manifests plus a rendered `vsphere-config-secret` ([templates/csi/vsphere-config-secret.yaml.tpl](templates/csi/vsphere-config-secret.yaml.tpl), keyed off `var.vsphere_user`/`vsphere_password`/`vsphere_server` — hence those being duplicated into `terraform.tfvars` alongside the `VSPHERE_*` env vars the provider itself uses), then a `vsphere-csi` StorageClass targeting `var.vsphere_datastore_url` ([templates/csi/storageclass.yaml.tpl](templates/csi/storageclass.yaml.tpl)). It also demotes RKE2's bundled `local-path` StorageClass's default annotation, since two StorageClasses both marked default is ambiguous.

Two `modules/vm` settings exist specifically for CSI to work, both worth knowing if you ever change the source template:
- `enable_disk_uuid = true` — without it, the CSI node plugin can't reliably match a PV's backing VMDK to the node it's attached to.
- `hardware_version = 20` — vSphere CSI's disk-attach (CNS) operation requires virtual hardware **vmx-13 or newer**. If the template is stuck on an old hardware version (vmx-10 is what shipped here, from the vSphere 5.5 era), attaches fail with `DeviceUnsupportedForVmVersion` and a PVC-bound pod hangs in `ContainerCreating` indefinitely with no obvious error short of digging into the CSI controller's `csi-attacher` container logs. Pick a value your actual ESXi hosts support (`8.0.3` supports up to vmx-21; 20 leaves headroom without assuming the newest possible revision) — the vCenter version alone doesn't guarantee the *hosts* support the same range.
- `vsphere_datastore_url` is a `ds:///vmfs/volumes/<uuid>/` path, not the datastore's display name, and isn't exposed by the `vsphere_datastore` data source. Find it via the datastore's `summary.url` property (a short pyvmomi or govc script against the same vCenter).

## Registry

`null_resource.install_registry` deploys `registry:2` in-cluster (namespace `registry`, PVC on `vsphere-csi`, exposed as a `NodePort` Service) with htpasswd basic auth (`registry_username`/`registry_password`, hashed via Terraform's native `bcrypt()` — no external `htpasswd` tool needed). Nodes pull from it at `https://<control_plane_vip>:<registry_node_port>` (default port `30500`) — this works from any node because NodePort is exposed by kube-proxy cluster-wide, independent of which node currently holds the kube-vip VIP. `local.registry_address` in [locals.tf](locals.tf) is that address. **The registry now serves real TLS**, not plaintext HTTP: `tls.tf` generates a self-signed internal CA via Terraform's `tls` provider, and that CA's public cert is distributed to every node (`registry_ca_cert_b64` in the cloud-init templates and pushed via the `configure_registry_mirror_*` day-2 provisioners) so containerd's mirror config trusts it. `templates/registries.yaml.tpl` renders both the `https://` mirror config and the `configs.auth` block so containerd authenticates automatically on every node — without the latter, pulls fail with `no basic auth credentials`. See [SECURITY.md](SECURITY.md) for the full current posture; the CA's private key never leaves Terraform state and this is not a substitute for a publicly-trusted cert for anything reachable from outside this network.

Getting an image *into* it: there's no `docker` CLI on the nodes. Use RKE2's bundled `ctr` against its containerd socket, e.g. from any node:
```bash
CTR='sudo /var/lib/rancher/rke2/bin/ctr -a /run/k3s/containerd/containerd.sock -n k8s.io'
$CTR image pull --platform linux/amd64 docker.io/library/someimage:tag
$CTR image tag docker.io/library/someimage:tag <registry_address>/someimage:tag
$CTR image push --skip-verify -u <registry_username>:<registry_password> --platform linux/amd64 <registry_address>/someimage:tag
```
Since the registry TLS fix, `--plain-http` no longer works here at all (`400 Bad Request` — the listener is HTTPS-only now) and a plain `--skip-verify`-only push fails auth (`401 Unauthorized`, `no basic auth credentials`) — `ctr image push` doesn't inherit containerd's own configured mirror credentials/CA trust, so both `--skip-verify` (the CA isn't in the node's system trust store) and `-u user:pass` are required together, verified directly against a live push on 2026-08-26. **Verify your credentials actually match first** — `curl -sk -u <user>:<pass> https://<registry_address>/v2/` should return `{"repositories":...}` or `{}`, not a 401; this repo has hit live drift where `terraform.tfvars`' `registry_username`/`registry_password` didn't match the deployed `registry-htpasswd` Secret's actual contents (`kubectl get secret -n registry registry-htpasswd -o jsonpath='{.data.htpasswd}' | base64 -d` to check what's actually live).

`--platform linux/amd64` on both pull and push matters: pulling a multi-arch tag without it stores the full manifest list, and pushing that list fails with `content digest ... not found` because `ctr` never actually downloaded the other platforms' blobs.

Getting registries.yaml onto nodes that already existed when this config was added is **not** something a plain reboot can do — see the cloud-init rough edge below. `null_resource.configure_registry_mirror_workers`/`_cp0`/`_cp1`/`_cp2` push the file over SSH and restart the RKE2 service directly instead (CP nodes one at a time, same quorum reasoning as everywhere else in this file). This is harmless to leave running on every apply, including against brand-new nodes that already got the file via cloud-init.

**Real incident(s)**: the registry's PVC hit ext4 journal corruption (`Aborting journal`, `input/output error` on reads) **three separate times** across this repo's history — first from repeated back-to-back `kubectl apply`/pod-recreate cycles while first standing it up, then twice more from unrelated node reboots during later rollouts, with the third occurrence happening with *no* intervening reboot at all. Each time the fix was the same (delete + recreate the PVC and Deployment; there was never real data worth recovering), but by the third occurrence it was clear this isn't specific to the registry or to reboots — this was the same `LAB-CL01`/`LAB-LUN01` single-path iSCSI incident described in the "Storage" section above, now resolved by the move to `K8S-CL01`. If this workload starts holding real data, don't casually re-`apply` its Deployment while a previous rollout might still be settling — a `Recreate`-strategy Deployment detaches/reattaches its volume on every pod recreation — but also don't assume fixing that eliminates the risk.

`terraform plan` used to periodically show a `disk { label = "orphaned_disk_N" -> "<remove, keep disk>" }` change on whichever node happens to be running the registry (or any other CSI-backed workload) at the time — Terraform noticing the CNS-attached VMDK it doesn't manage and normalizing its own bookkeeping label. This was believed to be a harmless relabel-only, no-VM-impact change. **It isn't.** CNS actively attaches/detaches these disks as pods get scheduled/rescheduled, so the disk list Terraform saw at plan time can already be stale by apply time; one real apply hit that race, failed mid-reconfigure with `Invalid configuration for device '0'`, and left all 6 worker VMs powered off until manually powered back on via pyvmomi. `disk` is now in `modules/vm/main.tf`'s `lifecycle.ignore_changes` for exactly this reason — Terraform no longer touches these labels at all, at the cost of no longer managing boot-disk resizes via `var.disk_gb` either (not something this repo does anywhere currently).

## External access (MetalLB)

`null_resource.install_metallb` installs [MetalLB](https://metallb.io/) (native manifest, L2/ARP mode — same mechanism `kube-vip` already uses for the control-plane VIP) and hands it `var.metallb_ip_range` as its address pool. It also creates `ingress-nginx-lb`, a `type: LoadBalancer` Service in `kube-system` selecting RKE2's bundled `rke2-ingress-nginx-controller` DaemonSet, which otherwise has **no** Service of its own — only an admission-webhook Service exists by default.

Worth knowing before assuming this was strictly necessary: the ingress-nginx DaemonSet's containers already declare `hostPort: 80`/`443` (confirmed via `kubectl get ds -n kube-system rke2-ingress-nginx-controller -o jsonpath='{.spec.template.spec.containers[0].ports}'`), which means **it was already reachable on every node's own IP** before MetalLB existed (`curl http://<any-node-ip>` returns nginx's default 404). MetalLB's actual value-add here is a single stable floating IP instead of requiring callers to know all N node IPs — plus general `type: LoadBalancer` capability for any future Service, not just ingress.

The IPAddressPool/L2Advertisement config apply can fail on the very first attempt because MetalLB's validating webhook isn't accepting connections yet even after its Deployment reports "rollout complete" — the remote-exec script retries (12× / 5s apart) rather than treating the first failure as fatal.

Same IP-range caution as `control_plane_ip_addresses`/`worker_ip_addresses`: `metallb_ip_range` must be verified free and excluded from DHCP, not guessed.

## Enterprise hardening

A few production-readiness gaps were closed after the initial build, all additive and independently verified against the live cluster:

- **`vsphere_compute_cluster_vm_anti_affinity_rule.control_plane`** aims to keep the 3 control-plane VMs on 3 different ESXi hosts — without it, DRS is free to stack all 3 etcd members on one host, silently defeating the entire point of "3-node HA." It genuinely needs **3+ hosts** to mean anything; on the current `K8S-CL01` (2 hosts, see "Storage" above) it's set `enabled = false`, since spreading 3 VMs across 2 hosts is arithmetically impossible and an *enabled* rule (even `mandatory = false`) still hard-blocks power-on/migration when it can't be satisfied — see the anti-affinity rough edge below. If this cluster ever grows to 3+ hosts, re-enable it (`enabled = true`, `mandatory = true`).
- **`etcd_snapshot_schedule_cron`/`etcd_snapshot_retention`** enable RKE2's built-in etcd snapshotting (local disk only — see the variable descriptions in [variables.tf](variables.tf) for why this isn't real off-node DR by itself).
- **`reserve_memory`/`cpu_share_level`** on `modules/vm`, set for control-plane nodes only: a full memory reservation (no ballooning/swapping) plus high CPU shares, guarding etcd's latency-sensitive disk I/O against noisy-neighbor contention on shared hosts. A hard MHz `cpu_reservation` was deliberately avoided since it isn't portable across heterogeneous hosts.
- **`vsphere_tag_category.managed_by`/`vsphere_tag.terraform_managed`** mark every VM this repo creates at the vCenter level, applied via `modules/vm`'s `tag_ids` variable — visible in the vSphere client independent of anything in Terraform state.
- **`.github/workflows/terraform.yml`** runs `fmt -check`, `validate`, and `tfsec` on every push/PR. No vCenter credentials involved (`init -backend=false`), so it's safe to run against a public repo/fork without provisioning any secrets.
- **Registry basic auth** (`registry_username`/`registry_password`) — see the Registry section below.
- **MetalLB** for `type: LoadBalancer` Services — see the External access section below.

**Rollout lesson**: `null_resource`s that push config over SSH (`configure_registry_mirror_*`) need an explicit `triggers` block hashing the content they push. Without one, changing what the referenced `local` value renders to (e.g. adding auth to `registries_config_yaml`) does **not** cause Terraform to re-run the provisioners against nodes the resource already succeeded on — `null_resource` has no other way to detect that the rendered file changed underneath it, and a stale push silently ships an outdated config to already-provisioned nodes indefinitely. The same applies if the *provisioner script itself* changes without the pushed content changing (e.g. adding a `chmod`/`rm` step) — `config_hash` alone won't catch that, which is why those triggers also carry a `script_version` marker to bump by hand when the script logic changes.

## Security & compliance (CISA/NSA Kubernetes Hardening Guidance-aligned)

**→ See [SECURITY.md](SECURITY.md) for the full posture**: admission control (Kyverno), vulnerability scanning (Trivy-Operator), runtime threat detection (Falco), registry TLS, multi-tenant RBAC/isolation, an OIDC authentication hook, ingress WAF/rate-limiting, and — critically — an honest checklist of what's still needed before this cluster should ever be exposed to the public internet. This section covers the initial pass; SECURITY.md is the living, complete document.

A security/compliance pass against this repo found and fixed several gaps, cross-referenced against [CISA/NSA's Kubernetes Hardening Guidance](https://www.cisa.gov/resources-tools/resources/kubernetes-hardening-guidance) (which the RKE2 `cis` profile below is itself built to satisfy) and general NIST 800-53 control families (SC-8 transmission confidentiality, SC-28 protection at rest, AU-2 audit logging, AC-6 least privilege).

**Fixed in code:**
- **`/etc/rancher/rke2/registries.yaml` was world-readable (`0644`) on every node**, despite carrying the in-cluster registry's plaintext password in its `configs.auth` block (`templates/registries.yaml.tpl`). Now `0600` in both cloud-init templates. Also fixed on the day-2 SSH-push path (`configure_registry_mirror_*` in [main.tf](main.tf)) so this reaches the *already-running* cluster without needing a node replacement.
- **Credential-bearing files were left behind in `/tmp` indefinitely** by every provisioner that pushes them — the vCenter password (via the CSI config secret), and the registry password (via `registries.yaml`), on every node that ever ran `terraform apply`. All `file`-provisioner + `remote-exec` pairs in [main.tf](main.tf) now `chmod 600` immediately on upload and remove the file (`shred -u` where available) once applied.
- **No etcd secrets-encryption-at-rest.** `secrets-encryption: true` added to the control-plane `config.yaml` template — RKE2 auto-manages an AES-CBC key for encrypting `Secret` objects in etcd. This is explicitly named in CISA/NSA's guidance. **Template-only**: takes effect for fresh nodes only, same as everything else in `config.yaml` — see the etcd-identity rough edge above before assuming a plain `apply` retrofits this onto the live cluster. Enabling it on the already-running cluster is a separate, deliberate day-2 operation (`rke2 secrets-encrypt enable` on each server node, one at a time, followed by `rke2 secrets-encrypt rotate`/`reencrypt`) — not something to trigger as a side effect of an unrelated apply.
- **No Kubernetes API audit logging.** Added a baseline audit policy (`/etc/rancher/rke2/audit-policy.yaml`, `RequestResponse` level for `secrets`/`configmaps`/`serviceaccounts`/RBAC objects, `Metadata` level for everything else, `events` skipped entirely to control log volume) plus the matching `kube-apiserver-arg` flags. Same fresh-node-only caveat as above.
- **SSH hardening relied entirely on the base Ubuntu cloud image's own defaults.** Added explicit `ssh_pwauth: false` / `disable_root: true` to both cloud-init templates — defense-in-depth rather than trusting an unstated image default to stay that way.
- **GitHub Actions workflow had no explicit `permissions:` block**, meaning the `GITHUB_TOKEN`'s scope depended on org/repo-level defaults rather than being pinned in the workflow itself. Added `permissions: contents: read` at the workflow level (neither job needs to write anything).
- **Added `var.rke2_cis_profile`** (opt-in, defaults `false`): wires RKE2's built-in `profile: cis` mode, RKE2's own mapping of the CIS Kubernetes Benchmark. Left off by default because it can change what already-running workloads are permitted to do (e.g. `hostNetwork`/privileged pods like `kube-vip` and MetalLB's speaker), so flipping it is a deliberate choice, not a silent one — and like every other `config.yaml` change, it only takes effect on genuinely fresh nodes.

**Documented as accepted risk (not code-fixable without a real functional tradeoff):**
- **`ubuntu` user has passwordless, unrestricted sudo** (`sudo: "ALL=(ALL) NOPASSWD:ALL"` in both userdata templates). Required for Terraform's unattended `remote-exec` provisioners (no TTY available for a sudo password prompt). Compensating controls: SSH is key-only (`ssh_pwauth: false`, no password auth possible at all), root login is disabled, and access depends on possessing `var.ssh_private_key_path`.
- **`vsphere_allow_unverified_ssl`** — defaults to `false` (secure by default) in `variables.tf`, but this lab's live `terraform.tfvars` sets it `true` because `vcenter` presents a self-signed certificate. This disables TLS verification on both the Terraform provider's connection to vCenter *and* the in-cluster CSI/CCM's connection (same `insecure-flag` in `templates/csi/vsphere-config-secret.yaml.tpl`) — a real MITM exposure on the vCenter management path. The compliant fix is operational, not code: issue vCenter a certificate from a trusted internal CA (or import that CA into the trust store used by whatever runs `terraform apply`) rather than disabling verification. Left as an explicit per-environment opt-in rather than silently accepted.
- ~~In-cluster registry is plain HTTP, no TLS~~ — **fixed**: the registry now serves real TLS behind a self-signed internal CA (`tls.tf`), distributed to every node so containerd trusts it. See the Registry section above and [SECURITY.md](SECURITY.md) for details; the CA is not a substitute for a publicly-trusted certificate for anything reachable from outside this network.

## Known rough edges to be aware of when editing

- `network_interface_name` (default `ens192`) is a guess at the guest NIC name for VMXNET3 adapters on Linux; it must match whatever the actual template produces, and isn't derived from anything Terraform can see.
- `wait_for_primary`'s remote-exec provisioner requires SSH connectivity from wherever `terraform apply` runs to the control-plane VIP subnet, and a private key at `var.ssh_private_key_path` matching `var.ssh_public_key`. Provisioners are inherently best-effort in Terraform (no state tracking, reruns on taint) — if bootstrap ordering ever needs to be more robust, that's the seam to reconsider.
- `rke2_version` is passed straight to `get.rke2.io`'s `INSTALL_RKE2_VERSION`; there's no validation that the value is a real RKE2 release.
- `wait_for_primary`'s readiness check tests raw TCP reachability on the RKE2 supervisor port (9345) rather than parsing `/readyz`'s HTTP response — RKE2 disables anonymous auth by default, so an unauthenticated `curl .../readyz` always 401s and a naive `grep -q ok` loops forever even on a healthy cluster.
- **A plain reboot never re-delivers a changed `write_files`/`runcmd` entry to a node that's already booted once.** Cloud-init's per-instance stage (which is what write_files and runcmd both run under) is gated by a marker file cloud-init leaves on disk, keyed off `instance-id` — it runs exactly once per instance-id per disk, not on every boot. So editing `templates/cloud-init/*.tpl` to add something new, then reconfiguring `extra_config.guestinfo.userdata` on an *existing* VM, produces a real, harmless reboot that changes nothing: the file never gets written, because cloud-init sees the same instance-id + an existing marker and skips the whole stage. This is exactly why [main.tf](main.tf) has separate `configure_registry_mirror_*` null_resources that push `registries.yaml` directly over SSH rather than relying on cloud-init to pick it up — that's the only way to reach nodes that predate the config change. New template edits only take effect automatically for genuinely fresh clones (a brand-new disk has no marker regardless of instance-id).
- **Never let `vsphere_virtual_machine.extra_config` update in place on a control-plane node that has already started RKE2.** If cloud-init reruns against a disk that already has etcd data on it (e.g. because only the `guestinfo.metadata`/`guestinfo.userdata` changed and Terraform did an in-place update rather than a replace), RKE2 comes back up with etcd still remembering its *old* IP/member identity and refuses to start — "this server is a not a member of the etcd cluster. Found ... expect: ...", looping forever. The fix is `terraform apply -replace=<that resource address>` to force a genuinely fresh clone, not just re-editing config and re-applying.
- The source template (built from Ubuntu's official cloud-image OVA) carries vApp properties in its OVF, so `modules/vm/main.tf` includes a `cdrom { client_device = true }` block purely to satisfy vSphere's "this VM requires a client CDROM device to deliver vApp properties" clone-time check — even though this module ignores vApp properties entirely and drives cloud-init via `extra_config`/GuestInfo instead.
- When a new control-plane node joins etcd, RKE2 triggers a resync of the control-plane static pods (kube-apiserver, etc.) cluster-wide to roll out updated certs/SANs. This produces a normal, self-healing minute-or-two window where already-`Ready` control-plane nodes flap through `activating`/connection-refused before settling — don't mistake it for a failure.
- `vsphere_virtual_machine` requires the target VM folder (`var.vsphere_folder`) to already exist — it will not create one implicitly. `main.tf` manages it explicitly via `resource "vsphere_folder" "vm_folder"` for exactly this reason.
- Don't trust a portgroup name or any placeholder IP scheme (including the ones in `terraform.tfvars.example`) to reflect the real subnet — verify against the actual vSphere network before setting static IPs. A fast, low-risk way to confirm: temporarily boot one node with a DHCP-only `metadata` (network config `dhcp4: true` instead of static addressing) via `-replace`+`-target` on that one resource, read back whatever address VMware Tools reports in `guest_ip_addresses` (visible via `terraform state show`, no SSH needed), then revert. Picking "currently free" static IPs from a ping sweep alone isn't enough either — anything inside the DHCP pool's range can be reassigned later; get the pool boundaries excluded/reserved on the router/DHCP server for whatever static range you land on.
- **The `vapp { properties = { "password" = "", "public-keys" = "" } }` block in `modules/vm/main.tf` does not actually work, and `vapp` is now in that resource's `lifecycle.ignore_changes`.** The intent was sound — the source template carries a real leaked password (`Az@25101984`) and an unrelated third party's SSH public key baked into its OVF vApp properties, and blanking them on every clone was meant as a real fix, not cosmetic. But confirmed directly via pyvmomi (reading `config.vAppConfig.property` on a live node immediately after Terraform reported the reconfigure "complete"): vCenter keeps reporting the template's original plaintext values regardless — the blank-out never persists. Because a `vapp` reconfigure forces a real guest OS reboot, this meant **every single `terraform apply` was rebooting all 9 VMs for a change that silently never took effect** — discovered only after this cost an entire session's worth of cascading "connection refused"/etcd-timeout failures on unrelated installs that just happened to race those reboots. If re-attempting the blank-out, verify with a direct pyvmomi read-back after apply, not just a clean `terraform apply` exit code — Terraform reporting success here does not mean the value actually changed. The real fix is at the template level (rebuild it without the baked-in credentials); this is not something a live reconfigure can achieve for this template.
- Any `vsphere_virtual_machine` attribute change that forces a real hardware reconfigure (`hardware_version`, `enable_disk_uuid`, `vapp`, ...) can have **side effects the plan didn't predict**: on this cluster, upgrading `hardware_version` silently reset `num_cores_per_socket` and `tools_upgrade_policy` on every node it touched, which only showed up as new drift on the *next* `terraform plan` (not the one that made the original change). After any such reconfigure, re-run `terraform plan` once more before considering the rollout done — don't assume a clean apply means a clean end state.
- **Terraform cannot downgrade `hardware_version`, and this cluster's VMs have drifted upward on their own.** After a full destroy/rebuild, every node came up live at `vmx-21` even though `modules/vm/main.tf` requested `hardware_version = 20` — some part of the clone path (possibly VMware Tools' own upgrade behavior, since `tools_upgrade_policy` isn't pinned) pushed it past the requested value. Once that happens, *every* subsequent `terraform plan`/`apply` fails outright with `cannot downgrade virtual machine hardware version, current: 21, target: 20` until the config is bumped to match reality (now set to `21`, matching this cluster's actual live state and still within the ESXi 8.0.3 hosts' supported ceiling). If this recurs after a future rebuild, check `vm.config.version` via pyvmomi before assuming the configured value is what's actually running.
- The default 5-minute `wait_for_guest_net_timeout` can be too short after a hardware-version upgrade, since the guest's first boot on new virtual hardware is slower than a normal reboot; `modules/vm` sets it to 10 minutes. A `terraform apply` timing out here does not necessarily mean anything is wrong — check the VM's actual power/tools/IP state via pyvmomi before assuming failure, since the underlying vSphere task frequently completes fine after Terraform's own wait gives up.
- Any reconfigure applied to a running node (not just the initial clone) needs the same care as the etcd-corruption rough edge above re: **rollout order** — apply to workers first, then control-plane nodes one at a time (never in parallel), so etcd never loses quorum. `-target` on a resource also pulls in its Terraform *dependencies* (ancestors), not just the resource itself — e.g. targeting any `module.workers[n]` will also reconfigure `module.control_plane_primary`, since workers depend on `null_resource.wait_for_primary` which depends on it. Don't assume an apply only touched what you named; check `terraform state show` on anything upstream too.
- **A namespace-wide `default-deny-all` NetworkPolicy silently blocks any pod that doesn't get its own explicit egress rule — including one-shot init Jobs, which are easy to forget.** In `observe-dev` (not managed by this Terraform, but running on the cluster it provisions), every MinIO consumer (`mimir`, `loki`, `tempo`) had an explicit egress rule to `minio:9000`, but the `minio-init` bucket-creation Job never did. The symptom looked exactly like a deeper infra problem — a pod reachable from itself but from nothing else, surviving across pod restarts and a node change unchanged — because `minio`'s own policy correctly listed `minio-init` as an allowed *ingress* source, making the destination side look "authorized" while the source pod's egress was still fully blocked. NetworkPolicy requires both sides to agree; check the *source* pod's egress rules, not just the destination's ingress rules, before assuming a policy is correctly wired. Fixed by adding a dedicated `minio-init` NetworkPolicy egress rule; unrelated to the datastore corruption issue above.

### K8S-CL01 (vSAN) rough edges, found during the 2026-08-24 migration

- **Editing "vSAN Default Storage Policy" in place does not reliably take effect, even though the UI reports the edit saved and `terraform apply` reports success.** Confirmed directly: changed its `hostFailuresToTolerate` to 0 via the vSphere Client, re-verified the change was visible in the UI, then a VM clone against the same datastore still failed with `Cannot complete file creation operation` / `vob.vsan.clomd.needMoreFaultDomains2: There are currently 1 usable fault domains. The operation requires 2 more usable fault domains.` — the *default* policy assignment on the datastore hadn't actually changed (confirmed via `PbmQueryDefaultRequirementProfiles` over the PBM API: it was still pointing at the original policy object). **Assigning a *different* policy as the datastore's default** (`PbmAssignDefaultRequirementProfile`, or Datastore → Configure → General → Default Storage Policy → Edit) *does* reliably persist — editing an existing policy's own rules in place is what's unreliable, not the default-assignment mechanism itself. `main.tf` now references the working policy explicitly via `data "vsphere_storage_policy"` + `var.vsphere_storage_policy_name` rather than depending on whatever the datastore's default happens to be.
- **A storage policy's `proportionalCapacity` (Object Space Reservation) silently overrides `thin_provisioned = true` on vSAN.** `Management Storage Policy - Single Node` (the built-in policy that unblocks single-fault-domain object creation) carries `proportionalCapacity: 100` — full eager-zeroed-thick allocation — which took effect regardless of the VM disk's own `thin_provisioned` attribute, and wasn't obvious until `vsanDatastore` dropped from ~1TB to 90GB free (8.1%, triggering vCenter's own red "Datastore usage on disk" alarm) after cloning just 9 VMs. The fix was a custom policy (`hostFailuresToTolerate=0`, `proportionalCapacity=0`) created via the PBM API and set as the datastore default; the 9 already-thick VMs were then live-reconfigured onto it (`ReconfigVM_Task` with `vmProfile` + a matching `disk[].profile`) — a non-disruptive vSAN operation that reclaimed the wasted space via background resync, no VM downtime. Check `proportionalCapacity` on any custom or built-in policy before assuming `thin_provisioned` in Terraform is the last word on disk allocation.
- **`terraform-provider-vsphere`'s `storage_policy_id` (both the top-level VM attribute and the per-`disk` block attribute) is not reliably wired into the actual clone operation in this provider version** — setting it explicitly in Terraform did not stop clones from failing with the same fault-domain error the datastore's own broken default produced, while a raw pyvmomi clone with the identical profile explicitly set on `RelocateSpec.disk[].profile` succeeded immediately. Don't trust an explicit `storage_policy_id` in Terraform to override a bad datastore default at clone time — fix the datastore's actual default (previous bullet) and treat `storage_policy_id` in Terraform as defense-in-depth, not the primary mechanism.
- **A DRS anti-affinity rule that's merely `enabled = true, mandatory = false` still hard-blocks a power-on it can't satisfy, at least on this vCenter (8.0.3)** — confirmed by testing: with only 2 hosts and 3 control-plane VMs, powering a VM back on failed with `This operation would violate a virtual machine affinity/anti-affinity rule` / `vCenter Server was unable to find a suitable host` regardless of whether `mandatory` was `true` or `false`, and regardless of explicitly specifying a target host in the power-on call. Only `enabled = false` actually let the VM power on. The `mandatory`/soft-vs-hard distinction appears to only affect DRS's own migration *recommendations*, not its power-on admission check.
- **A cluster's EVC (Enhanced vMotion Compatibility) mode can end up set far below what the actual hosts support** (found stuck at `intel-merom` — 2006-era baseline — on hosts that are genuinely Sandy Bridge-generation Xeons, `E5-2620 0`, from 2012), and this silently hides modern CPU features (SSE4.1/SSE4.2/POPCNT/AVX) from every guest's `/proc/cpuinfo`/`lscpu`, regardless of the real hardware. Symptom was cryptic and had nothing obviously to do with CPU: a container crashing with `Fatal glibc error: CPU does not support x86-64-v2` (Falco's images require that baseline). Fixed by raising EVC to match the hosts' real generation (`ConfigureEvcMode_Task` via pyvmomi, or Cluster → Configure → VMware EVC) — but **raising EVC alone does nothing for already-running VMs**: a VM's exposed CPUID mask is fixed at power-on time, so every VM needs a genuine power off + power on (not a guest-level reboot) to actually pick up the new features. On a live control-plane, this means the same one-at-a-time rollout-order discipline as any other disruptive change (workers first, secondary control-plane nodes one at a time, primary last) to protect etcd quorum throughout.
- **A Kyverno admission webhook timeout that's hardcoded (not exposed via any Helm value or `kyverno` CLI flag in this chart version) can combine badly with a DaemonSet's burst pod creation.** A single, isolated pod-create request against Falco's actual (privileged, multi-container, multiple-hostPath-volume) pod spec consistently completed in well under a second — but the DaemonSet controller creating all 9 of Falco's pods in one concurrent burst intermittently exceeded Kyverno's fixed 10s webhook timeout on some of those requests, and because the webhook's `failurePolicy` is `Fail`, that hard-blocked pod creation on whichever nodes lost the race (`failed calling webhook "validate.kyverno.svc-fail": ... context deadline exceeded`), sometimes for many minutes at a stretch (the DaemonSet controller's own retry backoff can stretch past a single `helm upgrade --wait 5m`). The fix that actually worked: exclude the namespace from the relevant Kyverno policies (`templates/security/kyverno-baseline-policies.yaml` — `falco` is now alongside `kube-system`/`vmware-system-csi`/`metallb-system`), which reduces per-request evaluation work enough to avoid the timeout in practice, on top of being the structurally correct call anyway (Falco cannot run at all without privileged/root/hostPath access). If a burst-creating DaemonSet workload hits this again, manually creating its pods **sequentially** (one `kubectl apply` at a time, each targeting a specific node via `nodeName`, matching the DaemonSet's own labels/`ownerReferences`) sidesteps the concurrency entirely and can unblock a stuck rollout immediately.
- **A pod (or a controller pod like `vsphere-csi-controller`) that was already running on a node when that node's CNI/network stack broke can get stuck with a stale network namespace that a normal restart never clears — and it can look exactly like a completely unrelated failure.** This session hit the pattern three separate times after power-cycling nodes for the EVC fix above: a Falco pod stuck in `CrashLoopBackOff`/`Terminating` indefinitely (its DaemonSet's own controller pod, `rke2-canal`, was itself stuck `0/2 Unknown` on that node); a `vsphere-csi-controller` replica crash-looping ~once every 8 seconds with the exact `dial tcp 192.168.100.100:443: connect: connection timed out` signature that historically meant "vCenter is unreachable" (misleading — the *other* two replicas, on healthy nodes, could reach vCenter fine the whole time). In every case the fix was the same: `kubectl delete pod <name> --grace-period=0 --force` (a graceful delete alone can hang indefinitely) to force a fresh pod/sandbox once the node's actual networking (canal/CNI) was confirmed healthy first. Don't assume a `dial tcp ...: connection timed out` error to an external endpoint (vCenter, a container registry, anything) means that endpoint is actually unreachable — check whether *other* pods on *other* nodes can reach it fine first; if so, it's very likely this stale-sandbox pattern on one specific node, not a real network/target outage.
- **A `PersistentVolumeClaim` with `volumeBindingMode: WaitForFirstConsumer` (the `vsphere-csi` StorageClass's mode) will never trigger provisioning for a pod whose `spec.nodeName` was set directly at creation time.** The delayed-binding trigger lives in the *scheduler's* volume-binding plugin, which only runs when the scheduler actually performs the bind — a pod created with `nodeName` pre-set bypasses the scheduler (and that plugin) entirely, so the PVC just sits `Pending` forever with no error and no events beyond a repeating, silent `WaitForFirstConsumer` message. Confirmed by testing both ways side by side: identical PVC/pod spec, `nodeName` set directly → never bound; the same spec using `nodeSelector` (targeting the same single node, but leaving the scheduler in the loop) → bound and running within seconds. Use `nodeSelector`, not `nodeName`, whenever you need to pin a test pod to a specific node and still exercise real dynamic provisioning.
- **A cluster VIP change (e.g. moving clusters, as here: old VIP `192.168.100.10` → new VIP `192.168.100.40`) does not update any previously-fetched kubeconfig** — `kubeconfig.yaml` in this repo and `~/.kube/config` both keep pointing at the dead old address (`dial tcp <old-vip>:6443: connect: network is unreachable`) until explicitly regenerated via `terraform output kubeconfig_fetch_command`. This is easy to mistake for a real cluster outage right after a successful migration.
